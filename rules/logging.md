# 日志规则

## 一、职责与统一入口

日志由掌握事件语义的模块负责记录。底层通用组件不得推测上层业务含义，也不得将日志作为事件、状态或错误传播机制的替代品。

应用及各 Workspace Crate 直接使用 `tracing` 记录自身日志，不要求固定日志 Target。

日志订阅、过滤、格式、输出目标及持久化由宿主应用统一负责，内部 Crate 不得擅自安装第二套全局 Subscriber。

## 二、日志等级

根据事件性质选择日志等级，不单纯根据事件是否重要判断。

### ERROR：真实错误

用于记录已经发生的真实错误，应提供失败原因和必要的上下文；不以日志记录代替处理或传播。

错误日志的具体时机由当前调用层的处理职责决定，不为所有 Crate 预设错误 ID、源头唯一日志、传播阶段或统一生命周期。

### WARN：异常与风险

用于尚未构成真实错误，但存在明确异常、风险或功能受限的情况，包括环境条件异常、资源压力和可选能力受限。

WARN 不用于正常等待、取消、普通状态变化，也不得用于掩盖实际错误。

### INFO：业务操作与结果

用于记录具有明确业务语义的用户或程序操作及其结果，不以操作是否改变状态作为记录门槛。

明确语义的程序自动操作可以记录 INFO，必要时区分触发来源。INFO 描述业务含义，不记录 Pointer、Keyboard 等底层输入机制。

### DEBUG：程序运行与执行过程

用于有诊断价值的启动、就绪、退出、状态转移、任务生命周期和实际错误处理结果。

DEBUG 不要求记录每次函数调用、ECS System 执行或内部状态同步，也不要求每个 Plugin 一定输出一条注册日志。

### TRACE：临时开发诊断

TRACE 仅用于开发期间的细粒度或高频诊断，例如逐帧更新、频繁事件和中间状态。

开发任务完成后必须移除临时 TRACE 调用。正式提交的应用和库代码不得保留 TRACE 调用，包括通过条件编译隐藏的调用。

使用 Clippy `disallowed_macros` 检查，不另外开发专用 Lint。

## 三、操作与执行生命周期

### 业务操作

业务操作日志描述实际请求和取得的结果。同步操作可在结果确定时记录一次。

异步、延迟或分阶段操作应区分发起与最终结果，不得在结果尚未确定时提前记录成功。

用户明确发起的操作即使未改变状态，也应记录实际未变化的结果。程序内部常规同步、重复设置和无业务意义的 No-op 不因此产生业务日志。

### 程序执行

程序内部执行过程使用 DEBUG，与业务操作 INFO 可以同时存在。自动触发的内部流程不得虚构用户操作日志。

### 线程与异步任务

只记录项目自身管理、与业务流程相关且具有明确生命周期的线程与异步任务。

根据实际执行情况记录启动、完成、取消请求、实际取消和结束等有诊断价值的节点。取消请求不等于取消完成，退出请求不等于线程结束。

不强制追踪 Bevy 内部任务调度、任务轮询或大量短期并行计算。用户操作产生的 INFO 与内部任务 DEBUG 应可按需关联，但不重复表达同一事实。

## 四、日志关联与内容

日志正文统一使用中文，动态信息采用英文命名的结构化字段，例如 `operation_id`、`task_id`、`entity`、`path`、`action`、`error`。

正文说明发生了什么，结构化字段提供必要上下文。同一次多阶段操作需要关联时使用一致且合适的业务标识，不规定所有事件必须有统一字段。

字段应足以识别操作、目标、关键参数及结果，但不得无必要地记录完整用户输入、敏感数据或大型数据内容。

不手动添加 `file`、`line`、`module_path`、`crate_name` 等已有 Tracing Metadata，由宿主决定显示方式。

## 五、重复记录与持续异常

同一日志不应重复描述已经记录且没有新增诊断价值的事实。

对于持续存在的同一异常状态：

- 正常进入异常时记录一次相应等级日志。
- 持续期间不因重复检查反复记录。
- 实际恢复时记录一次 DEBUG。
- 恢复后再次发生时重新记录。

持续状态去重不得抑制新产生的独立错误。正常等待不代表异常已经恢复，Entity 销毁也不自动产生恢复日志。

## 六、日志过滤与持久化

正常运行时宿主应默认保存自身 DEBUG、INFO、WARN 和 ERROR 日志。TRACE 默认关闭，仅开发诊断时按需启用。

第三方依赖日志可以单独设置过滤规则，避免无关信息淹没应用日志。

持久化配置不得在缓冲区满时静默丢弃必要的错误记录；日志后端失败时必须采取明确、可观察的降级或失败处理。
